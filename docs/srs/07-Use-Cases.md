# Use Cases

## Overview

This document describes the key use cases of the KISS Vocational Training Management Portal, detailing actor interactions and system behavior.

## Use Case Model

### Actors

| Actor | Role | Responsibility |
|-------|------|-----------------|
| Student | End-user | Enroll in courses, track progress, view grades |
| Teacher | Instructor | Mark attendance, grade students, manage course |
| Admin | System Operator | Configure system, manage allocations, run reports |

## Use Cases by Actor

### Student Use Cases

#### UC-STU-001: Log In to System
**Actor**: Student

**Preconditions**:
- Student account created by admin
- System is accessible

**Main Flow**:
1. Student navigates to login page
2. Enters email and password
3. System validates credentials
4. System determines role and redirects to dashboard
5. Student views personalized dashboard

**Postconditions**:
- Student is authenticated
- Session created with JWT token

---

#### UC-STU-002: Enroll in Course
**Actor**: Student

**Preconditions**:
- Enrollment window is open
- Student is within staggered enrollment window
- Course offering exists with available capacity

**Main Flow**:
1. Student logs in
2. Navigates to Enrollment module
3. Views available courses with capacity and deadline
4. Selects desired course
5. Confirms enrollment
6. System validates eligibility and capacity
7. System saves enrollment
8. Confirmation email sent
9. Student redirected to dashboard

**Alternate Flow (A1)**: Enrollment window closed
1. After step 2, system displays "Enrollment window closed"
2. Shows dates of next enrollment window

**Alternate Flow (A2)**: Course capacity full
1. After step 5, system shows "Course at capacity"
2. Student can view waitlist status

**Postconditions**:
- Enrollment record created
- Email confirmation sent
- Course appears in student dashboard

---

#### UC-STU-003: View Progress
**Actor**: Student

**Preconditions**:
- Student is enrolled in at least one course

**Main Flow**:
1. Student logs in
2. Navigates to Progress module
3. Selects enrolled course
4. Views:
   - Attendance percentage
   - Published grades (component-wise and overall)
   - Course completion status
   - Certificate status (if available)

**Postconditions**:
- Student reviews progress data

---

#### UC-STU-004: Submit Grievance
**Actor**: Student

**Preconditions**:
- Student is enrolled in at least one course

**Main Flow**:
1. Student navigates to Grievance Center
2. Clicks "Lodge Grievance"
3. Selects grievance category
4. Enters detailed description
5. Selects severity level
6. Submits grievance
7. System sends confirmation email

**Postconditions**:
- Grievance recorded with timestamp
- Status set to "Submitted"
- Email confirmation sent

---

#### UC-STU-005: Submit Course Feedback
**Actor**: Student

**Preconditions**:
- Feedback form available for enrolled course
- Admin has created feedback form

**Main Flow**:
1. Student navigates to Feedback section
2. Selects enrolled course
3. Views feedback form questions
4. Answers all required questions (rating/text)
5. Submits feedback
6. System records feedback as anonymous

**Postconditions**:
- Feedback submitted and recorded
- No student identification stored
- Admin can view aggregated feedback

---

#### UC-STU-006: Download Certificate
**Actor**: Student

**Preconditions**:
- Course is marked as complete by teacher
- Certificate generated by system

**Main Flow**:
1. Student logs in
2. Navigates to Certificates section
3. Views list of earned certificates
4. Clicks "Download" on certificate
5. PDF generated with all fields populated
6. PDF downloads to student's device

**Postconditions**:
- Certificate PDF downloaded successfully

---

### Teacher Use Cases

#### UC-TEA-001: View Assigned Courses
**Actor**: Teacher

**Preconditions**:
- Teacher assigned to at least one course
- Current semester is active

**Main Flow**:
1. Teacher logs in
2. Navigates to Teacher Dashboard
3. Views list of assigned courses
4. For each course:
   - Batch details (number of students, timing)
   - Student count
   - Course status
5. Can click on course to view details

**Postconditions**:
- Teacher reviews course assignments

---

#### UC-TEA-002: Take Attendance
**Actor**: Teacher

**Preconditions**:
- Teacher has assigned batch
- Course is ongoing (not completed)

**Main Flow**:
1. Teacher logs in
2. Navigates to Attendance section
3. Selects course and batch
4. Selects date (today's date by default)
5. Views list of all students in batch
6. Marks attendance: Present/Absent for each student
7. Can use bulk marking (Mark All Present, then toggle absents)
8. Saves attendance record
9. System calculates attendance percentage

**Alternate Flow (A1)**: Editing past attendance
1. After step 4, teacher can select past date (≤ 7 days)
2. System shows existing attendance record
3. Teacher can modify and save (edit logged)

**Postconditions**:
- Attendance record saved
- Attendance percentage updated

---

#### UC-TEA-003: Enter Grades
**Actor**: Teacher

**Preconditions**:
- Grading scheme defined by admin
- Teacher has batch of students
- Course is ongoing

**Main Flow**:
1. Teacher logs in
2. Navigates to Gradebook
3. Selects batch
4. Gradebook displays: Student list, all grade components, max marks
5. Teacher enters marks for each component
6. System validates marks against component maximum
7. Teacher can save multiple times (remains in Draft)
8. Teacher reviews final marks

**Postconditions**:
- Grades saved in Draft state
- Can still be edited before publication

---

#### UC-TEA-004: Publish Grades
**Actor**: Teacher

**Preconditions**:
- Gradebook is in Draft state
- At least one mark entered for at least one student
- Course deadline passed (optional validation)

**Main Flow**:
1. Teacher reviews gradebook in Draft state
2. Confirms all marks are accurate
3. Clicks "Publish" button
4. System validates (minimum marks requirement)
5. System calculates overall grade
6. System transitions to Published state
7. Email notification sent to all students
8. Grades become visible in student Progress module

**Postconditions**:
- Gradebook locked (no further edits)
- Students can view grades
- Email sent with notification

---

#### UC-TEA-005: Mark Course Complete
**Actor**: Teacher

**Preconditions**:
- Course end date has passed
- Grades published
- All students assessed

**Main Flow**:
1. Teacher logs in
2. Navigates to Manage Course
3. Selects course
4. Confirms course end date has passed
5. Reviews course completion checklist (attendance taken, grades published)
6. Clicks "Mark as Complete"
7. System validates all requirements met
8. System marks all enrolled students as completed
9. Triggers automatic certificate generation for all students
10. Email sent to all students

**Postconditions**:
- Course marked as completed
- Certificates generated within 1 hour
- Students receive notification

---

### Admin Use Cases

#### UC-ADM-001: Create Semester
**Actor**: Admin

**Preconditions**:
- Admin is logged in

**Main Flow**:
1. Admin navigates to Semester Management
2. Clicks "Create New Semester"
3. Enters semester details:
   - Name (e.g., "Spring 2026")
   - Start date
   - End date
4. Configures:
   - Course offerings
   - Seat configuration
   - Batch configuration
   - Teacher assignments
   - Grading schemes
   - Feedback forms
   - Enrollment windows
5. Reviews configuration summary
6. Confirms and saves semester

**Postconditions**:
- Semester created with full configuration
- Configuration available for enrollment window opening

---

#### UC-ADM-002: Create Course Offering
**Actor**: Admin

**Preconditions**:
- Semester exists
- Base course already created

**Main Flow**:
1. Admin navigates to Course Offerings
2. Selects semester
3. Clicks "Add Course Offering"
4. Selects base course
5. Configures:
   - Total capacity
   - Number of batches
   - Seats per batch
   - Assign teacher to each batch
6. Sets enrollment window dates
7. Sets roll-number ranges for staggered enrollment
8. Saves course offering

**Postconditions**:
- Course offering created
- Batches automatically created
- Enrollment window configured

---

#### UC-ADM-003: Define Grading Scheme
**Actor**: Admin

**Preconditions**:
- Semester exists
- Course offering exists

**Main Flow**:
1. Admin navigates to Grading Schemes
2. Selects course offering
3. Clicks "Define Scheme"
4. Adds grade components:
   - Component name, max marks, weight percentage
   - Example: Attendance (10, 10%), Activity (10, 10%), Projects (20, 40%), Final (60, 40%)
5. Validates weight sum equals 100%
6. Saves scheme

**Postconditions**:
- Grading scheme defined
- Teachers use scheme for marking

---

#### UC-ADM-004: Open Enrollment Window
**Actor**: Admin

**Preconditions**:
- Course offering configured
- Enrollment window dates set

**Main Flow**:
1. Admin navigates to Enrollment Windows
2. Selects course offering
3. Clicks "Activate Window"
4. Confirms window dates
5. Confirms roll-number ranges
6. Activates window
7. Sends notification to students

**Postconditions**:
- Enrollment window activated
- Students can enroll
- Dashboard shows active window

---

#### UC-ADM-005: Run Batch Allocation
**Actor**: Admin

**Preconditions**:
- Enrollment window closed
- Enrollments collected

**Main Flow**:
1. Admin navigates to Allocation
2. Selects course offering
3. Clicks "Run Allocation"
4. System prompts for confirmation
5. Confirms allocation run
6. System executes:
   - Fetches all enrollments
   - Randomizes enrollment list
   - Fills batches respecting capacity
   - Creates allocation records
7. Allocation completes, report generated
8. Email sent to all students with allocation

**Alternate Flow (A1)**: Insufficient capacity
1. If enrollments > total seats
2. System alerts admin
3. Admin can:
   - Reduce enrollments (waitlist)
   - Increase capacity (if possible)
   - Abort and reconfigure

**Postconditions**:
- All students allocated to batches
- Allocation report generated
- Emails sent

---

#### UC-ADM-006: Approve Batch Switching Request
**Actor**: Admin

**Preconditions**:
- Batch switching request submitted by student

**Main Flow**:
1. Admin navigates to Batch Switching Requests
2. Views list of pending requests
3. Selects request to review:
   - Current batch, requested batch, reason
4. Checks capacity of target batch
5. Approves or rejects
6. Adds optional comment
7. Submits decision

**Postconditions**:
- If approved: Student allocation updated
- Email notification sent to student
- Request marked as resolved

---

#### UC-ADM-007: Generate Reports
**Actor**: Admin

**Preconditions**:
- Sufficient data exists

**Main Flow**:
1. Admin navigates to Reports
2. Selects report type:
   - Certificate Report
   - Student Report
   - Course Report
3. Selects filters:
   - Date range
   - Semester
   - Specific course/student
4. Generates report
5. Can preview or export (PDF/CSV)

**Postconditions**:
- Report generated and available for download

---
